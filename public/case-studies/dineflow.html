Overview

What DineFlow is — and why it's more than a UI project

I built DineFlow to explore what it takes to move from a visually polished frontend to a functioning business application — persistent data, server-side logic, authentication, and real operational workflows, not just a UI that looks finished. It isn't a stand-in for a business idea I never tested: I designed the system, connected every layer myself, integrated three external services, and I'm the one who found and fixed the bugs before they reached a user — including one caught while writing the "Bugs Found" section of this very case study (see below).

Customers browse a menu, order, pay online or on delivery, and track their order status in real time. The restaurant's side manages the entire menu, watches orders arrive live, moves orders through a status pipeline, reconciles Cash on Delivery payments, and reads sales analytics — all behind real authentication, not a hidden link.

Customer Experience

Menu browsing with search & filters, cart, checkout with real online payment, live order tracking, order history behind login.

Customer actions are processed through server-side logic before anything is written to persistent storage — the frontend never talks to the database directly. Prisma enforces structured relationships between users, menu items, categories, and orders, while every route handler validates the request shape and checks authorization before executing a mutation. Engineering Challenges

Four problems that don't show up in a feature list

Business Logic

Protecting business logic from the client

The client submits which items and quantities were selected — never what they cost. Every order's item prices, subtotal, and delivery fee are recalculated server-side from the live Food and Settings tables at the moment the order is created; the request body's own price fields exist only for shape validation and are never used to charge anyone anything. An item that's been deleted or marked unavailable since it was added to the cart blocks the order outright rather than silently accepting stale data.

State Management

Modeling the order lifecycle as two independent states

An order has a fulfillment status (Placed → Confirmed → Preparing → Ready → Completed, or Cancelled) and a payment status (Pending, Paid, Failed) — modeled as two separate fields rather than one combined status. That's what makes it possible to represent a real Cash on Delivery order correctly: fully confirmed and being prepared, while payment is still genuinely pending until the driver collects it. Collapsing them into a single enum would have made that state unrepresentable.

Access Control

Authentication & authorization for two different audiences

Customers and restaurant staff share the same login system but not the same permissions — one role field, checked at two independent layers: route middleware that redirects non-admin visitors before an admin page ever renders, and a server-side check on every mutating admin API route underneath it. Guest checkout deliberately doesn't require an account — forcing a signup just to order food is exactly the friction the checkout flow was built to avoid — while a logged-in customer's own orders are still linked automatically via their session, never a client-supplied id.

Resilience

Handling failure in three external integrations

A payment gateway, an email provider, and cloud storage all sit outside this app's control, and each is isolated so a failure in one can't cascade. Every email send is wrapped so a Resend outage can only ever skip an email, never fail a checkout or block an admin action. Payment confirmation doesn't rely solely on the customer's browser redirecting back after paying — a server-to-server webhook runs independently as a fallback, and both paths share the same idempotency guard so a payment can never be double-processed no matter which one fires first, or if both do.

Under The Hood

What happens behind the button

Three real user actions, traced from the click to the database and back.

Customer places an order

User sees: Add to cart → Checkout → Place Order

Form validated client-side→ POST /api/orders→ Zod validates request shape→ Server re-prices every item from the database→ Order + items written to Postgres→ Confirmation email sent (Cash) or payment session started (Card)

Customer pays online

User sees: Redirected to SSLCommerz → enters card details → redirected back

Browser redirects back with a transaction id→ Server validates the transaction AND amount against SSLCommerz's API→ Order marked PAID only if both check out→ Independent IPN webhook confirms the same thing server-to-server→ Idempotency guard — whichever path arrives first wins, never both

Admin updates an order's status

User sees: Selects "Preparing" from a dropdown on the Orders page

PATCH /api/orders/[id]→ Server checks admin role (middleware + route-level)→ Status compared against the previous DB value, not the request→ Order row updated→ Status-change email sent to the customer, only if it genuinely changed→ Customer's tracking page reflects it on its next poll

Security & Reliability

What's actually protected, and how

Specific, verifiable measures — not a generic "security is important" statement.

  • ✓ Every API route validates its input shape with Zod before touching the database — malformed requests are rejected with a 400, not silently coerced
  • ✓ Order pricing is recalculated server-side from the database at checkout — client-submitted prices are structurally present in the request but never trusted for anything financial
  • ✓ Admin-only actions are checked at two independent layers: route middleware, and a server-side role check on every mutating API route underneath it
  • ✓ Payment confirmation requires SSLCommerz's own server-to-server validation of both the transaction and the amount paid — a client-side "success" redirect is never sufficient on its own
  • ✓ Row Level Security is enabled on every database table, closing Supabase's public REST API even though the app itself never uses it — found and fixed after Supabase's own automated scanner flagged it as critical
  • ✓ Secrets — database credentials, API keys, the service-role key — live only in server-side environment variables; nothing with write access to the database ships to the browser
  • ✓ Order lookups by the public order number require the order's own email as a second factor, since the number alone is a short, guessable code
  • ✓ Login, registration, checkout, and the contact form are rate-limited at the edge against scripted abuse
  • ✓ The framework itself is kept current — a routine dependency audit surfacing a known vulnerability gets treated as urgent, not backlogged
Engineering Process

Built in verified, sequential phases

Each phase was scoped, built, deployed, tested against real infrastructure, and confirmed working before the next one started — not a single big-bang rewrite, and not "done" the moment the features worked.

Frontend prototype

Full customer + admin UI on realistic mock data, to validate every flow and get the design system right before touching a database.

Database & API layer

PostgreSQL schema via Prisma, 17 REST API routes replacing every mock data source, with Zod validation on every input.

Authentication & authorization

NextAuth.js sessions, bcrypt password hashing, route middleware, and server-side role checks on every admin-only endpoint.

Payment gateway integration

SSLCommerz sandbox — hosted checkout, server-to-server transaction validation, and a webhook for reliability, with a full success/fail/cancel/retry flow.

Media pipeline

Client-side image compression and cloud storage uploads for menu photos, replacing pasted stock-image URLs.

Transactional email

Automatic, fail-safe order confirmation, status-update, and restaurant-alert emails — verified via delivery logs, not just "it compiled."

Security hardening

Zod validation extended to every remaining route, edge-level rate limiting, Row Level Security across every table, order lookups hardened against enumeration, and every credential rotated off a shared development machine onto dedicated accounts.

Framework currency, QA & handover readiness

Migrated off an end-of-life Next.js version using official upgrade tooling, a full manual QA pass with real outside testers, and written documentation so either a non-technical owner or another developer could pick this up cold.

Architecture Decisions

Notable technical decisions

Data layer

Designing for a mock-to-real migration from day one

Every piece of catalog and order state was routed through dedicated Context providers from the very first line of frontend code, shaped to match the eventual database schema. The entire admin CRUD experience was fully built and tested before a database even existed — migrating to real API calls later was a contained, predictable change, not a rewrite.

Database

Serverless-safe Postgres connections

Supabase's connection pooler doesn't support prepared statements the way schema migrations expect. The project uses two distinct connection strings — a pooled connection for the running app (safe under Vercel's serverless concurrency) and a direct connection reserved for Prisma CLI migrations and backups — avoiding a class of connection-exhaustion bugs common in serverless + Postgres deployments.

Payments

A dual-callback pattern for payment reliability

The checkout flow doesn't rely solely on the customer's browser redirecting back after payment — if their connection drops right after paying, that redirect might never happen. A server-to-server webhook (IPN) runs independently of the customer's browser as a reliable fallback, sharing the same amount-verification and idempotency logic as the redirect path.

Media

Image compression without a native server dependency

Photo uploads are resized and compressed in the browser using the Canvas API before they're ever sent to the server — deliberately avoiding a native image-processing library like Sharp on the server side, which introduces real deployment risk on serverless platforms. A 12MB phone photo typically becomes a few hundred KB before it ever leaves the customer's — or admin's — browser.

Dependency management

Treating framework currency as a security requirement

A routine dependency audit surfaced that the project's Next.js version had reached end-of-life — permanently unpatched, with a critical vulnerability among the findings. The fix meant a real major-version migration (async request APIs, a renamed middleware convention, a coordinated React and ESLint upgrade), done on a branch, verified against a Vercel preview deployment, and merged only after a full manual re-test of every critical flow — the same discipline as any other production change, applied to "just" a dependency update.

Quality Process

Bugs found before they shipped

Real engineering isn't writing code that looks right — it's catching what's wrong before a user does. These were found during development, code review, and QA — not by a customer in production.

Caught while writing this case study

Rewriting this case study to accurately describe how business logic is protected meant checking the claim against the actual code — and finding it wasn't fully true yet. Item prices, the subtotal, and the total were trusted directly from the checkout request; nothing re-validated them against the real menu prices in the database. A tampered request could have checked out at any price.

Fixed before this case study went live — every price is now recalculated server-side from the database at order creation, and an item deleted or marked unavailable since being added to the cart blocks the order outright.

Caught by automated security scan

Every database table was publicly readable through Supabase's auto-generated API — including password hashes and customer personal data — despite the application itself never using that API. The gap existed purely because Row Level Security wasn't enabled.

Fixed — Row Level Security enabled across all nine tables with zero application code changes required, verified clean on a follow-up scan.

Caught in QA

A toast notification meant to show "incorrect email or password" never appeared, in any browser, in any mode. Confirmed step by step: the failed login request returned the correct error, the state-management code was provably updating (verified via direct console logging), and the styling classes involved were valid. The actual cause was a single missing folder in the Tailwind build config's content-scanning list — a component living just outside the paths Tailwind was told to scan, so its styles were silently never generated at all.

Fixed — one-line config change, verified by confirming the component's other styles rendered correctly afterward.

Caught in QA

Restaurants had no way to mark a Cash on Delivery payment as collected from the Payments page — the backend function for exactly this was already fully built and wired to the Orders page, but the Payments page (the more natural place to look) was purely read-only. A backend being "done" and a feature being reachable turned out to be two different questions, twice — the Orders page and the public demo account surfaced this same gap independently.

Fixed — the same reconciliation action now lives on both pages, restricted only to pending Cash on Delivery orders.

Caught in review

Order creation was briefly marking online payments as "paid" immediately at checkout, before the customer had even reached the payment gateway. Combined with how the failure-handling logic worked, this would have permanently prevented an abandoned or declined payment from ever being correctly marked as failed.

Fixed before deployment — every order now starts pending regardless of payment method; only a validated gateway confirmation marks it paid.

Caught in review

The original schema required every menu item to belong to a category with no way to remove that link — meaning deleting a category with active menu items would fail at the database level with a constraint error, contradicting what the admin UI already promised the user.

Fixed by making the relationship optional with proper cascading behavior, before it ever reached a real admin's hands.

Caught by production build

A production build on Vercel caught a genuine type mismatch between seed data and an evolved database schema that local development never surfaced — Next.js's production build runs a full TypeScript check that dev mode skips for speed.

Fixed and redeployed the same day.

What I Would Improve Next

Where I'd take this next

Every item on the original build roadmap — security hardening, a full QA pass, and handover documentation — is done. But "done" isn't the same as "nothing left to improve," and knowing the difference matters more than pretending otherwise.

Automated testing

The QA pass to date has been entirely manual. A real test suite — especially around the order-pricing and validation logic — would catch regressions before a human has to.

A CI pipeline

Vercel's preview deployments catch build failures, but there's no automated lint/test gate before a pull request is even reviewable.

Structured observability

Right now, a production issue would need a human to notice it. Real error tracking and logging would surface problems before a user reports them.

Verifying the payment integration against live documentation

The SSLCommerz integration is correct against training knowledge and works in sandbox testing, but hasn't been cross-checked line-by-line against their current API docs — I'd do that before any real transaction ever ran through it.

More granular admin roles

There's one ADMIN role today. A real restaurant likely wants a kitchen-staff view that can update order status without touching settings or financials.

Performance work as it scales

No caching layer exists yet beyond Next.js's own defaults — fine at today's scale, worth revisiting under real load.
